1. SYSTEM OVERVIEW
================================================================================

SHULEPULSE is a multi-tenant, multi-role School Management ERP system designed
for Kenyan schools. It provides a SaaS platform where a superadmin onboards
schools, and each school gets role-based access to student management, academics,
finance, HR, library, communication, and administrative modules.

PURPOSE:
- Centralized school management across multiple institutions
- Role-based dashboards for admins, teachers, parents, students, and staff
- Complete financial management (fees, accounting, payroll, AP, assets)
- Academic management (grades, exams, CBC, timetable, report cards)
- Parent and student portal access
- Multi-school superadmin platform management

STATUS: [IMPLEMENTED] — Fully functional multi-role SaaS platform

4. AUTHENTICATION & AUTHORIZATION
================================================================================

4.1 AUTHENTICATION FLOW
-----------------------

  User submits email + password
    -> supabase.auth.signInWithPassword()
    -> On success: fetch profile.role from profiles table
    -> Hard redirect to role's home route:
         superadmin     -> /superadmin
         admin          -> /admin
         deputy_admin   -> /deputy-admin
         bursar         -> /admin (default fallback)
         registrar      -> /admin (default fallback)
         reception      -> /reception
         hod            -> /hod
         teacher        -> /teacher
         class_teacher  -> /class-teacher
         parent         -> /parent
         student        -> /student
         librarian      -> /library

  Session bootstrap (authStore.init()):
    -> getSession() -> fetch profiles with joined schools
    -> Normalize roles array: profile.roles || [profile.role]
    -> Load grading config
    -> Subscribe to onAuthStateChange for token refresh

4.2 ROLE SYSTEM — 12 ROLES
----------------------------

  Role Key               Display Name        Home Route
  ---------------------------------------------------------------
  superadmin             Super Admin         /superadmin
  admin                  Admin               /admin
  deputy_administrator   Deputy Admin        /deputy-admin
  bursar                 Finance             /bursar
  registrar              Registrar           /registrar
  reception              Reception           /reception
  hod                    HOD                 /hod
  teacher                Teacher             /teacher
  class_teacher          Class Teacher       /class-teacher
  parent                 Parent              /parent
  student                Student             /student
  librarian              Library             /library

  DUAL ROLE MODEL:
  - Primary role: profiles.role (single TEXT value)
  - Multi-role array: profiles.roles (TEXT[])
  - Normalization: profile.roles || [profile.role]
  - RoleSwitcher component allows switching between roles

4.3 ROUTE PROTECTION (ProtectedRoute.jsx)
-----------------------------------------

  - While loading: spinner
  - No user: redirect to /
  - allowedRoles provided but no match: redirect to role's home route
  - Role check: profile.role === role OR profile.roles.includes(role)

  Route-to-role mapping:
    /superadmin      -> [superadmin]
    /admin           -> [admin, superadmin]
    /deputy-admin    -> [deputy_administrator]
    /bursar          -> [bursar]
    /registrar       -> [registrar]
    /reception       -> [reception, admin, superadmin]
    /hod             -> [hod]
    /teacher         -> [teacher]
    /class-teacher   -> [class_teacher]
    /parent          -> [parent]
    /student         -> [student]
    /library         -> [librarian]

4.4 ROLE SWITCHING (RoleSwitcher.jsx)
--------------------------------------

  - Only renders for multi-role users (roles.length > 1)
  - Updates profiles.role in DB (persists to DB, not session-only)
  - Full page reload to new role's route
  - RLS profiles_update_own policy permits this (no server-side check)

4.5 SCHOOL CONTEXT RESOLUTION
------------------------------

  Non-superadmin: profile.school_id -> profile.schools (joined)
  Superadmin: get_my_school_id() returns NULL; picks school via SchoolSwitcher
  SchoolSwitcher persists school_id to superadmin's profile row

4.6 EDGE FUNCTIONS (Account Provisioning)
------------------------------------------

  create-student-auth: Creates student login accounts
  create-parent-auth: Creates parent login accounts (currently bypassed,
                      client-side signUp used instead)
  generate-admin-link: Issues invite/setup links for admin accounts
  reset-user-password: Server-side password reset for staff
  reset-student-passwords: Bulk student password reset

  NOTE: Edge functions are NOT deployed via Supabase CLI (not installed).
  Parent accounts use client-side supabase.auth.signUp instead.

5. MULTI-SCHOOL ARCHITECTURE
================================================================================

5.1 SCHOOL ISOLATION
---------------------

  Core principle: Every business row has a school_id column.
  RLS policy pattern:
    (school_id = get_my_school_id()) OR (get_my_role() = 'superadmin')

  SECURITY DEFINER functions (migration 068):
    get_my_school_id() -> school_id from profiles where id = auth.uid()
                          Returns NULL for superadmin
    get_my_role()      -> role from profiles where id = auth.uid()

  Migration 070 patched ~40+ tables with superadmin bypass.

15. SYSTEM DATA FLOWS
================================================================================

STUDENT ADMISSION:
  Admin/Registrar fills admission form
    -> StudentForm.jsx validates input
    -> studentService.createStudentAuth() (edge function)
    -> supabase.from('students').insert()
    -> Student created in DB
    -> Optional: parent auth account created

PAYMENT RECORDING:
  Bursar selects student -> fee assessment
    -> FeesPage displays balance
    -> Payment form (method, amount, reference)
    -> supabase.from('fee_payments').insert()
    -> journal_entry_id linked (auto GL posting)
    -> Receipt generated (PDF)

EXAM CREATION & MARKS ENTRY:
  HOD creates exam type -> ExamSetup
    -> exam_type_config updated
  Teacher enters marks -> MarksEntry
    -> supabase.from('grades').upsert()
  HOD approves -> MarksApproval
    -> status updated to 'approved'

PAYROLL PROCESSING:
  Bursar configures statutory rates
    -> payroll_statutory_config updated
  Creates payroll period and run
    -> payroll_runs inserted
    -> payroll_lines calculated (PAYE, NSSF, SHIF, housing, NITA)
    -> Review -> Approve -> Post (GL journal entries)
    -> Payment request -> Process

REPORT CARD GENERATION:
  Teacher enters marks per subject
    -> grades table updated
  Admin/Teacher generates report card
    -> grading engine resolves class -> profile -> bands
    -> weighted aggregation (Opener 15% / Midterm 15% / End-Term 70%)
    -> ranking via precisionScore
    -> PDF generated with school header

LOGIN / AUTHENTICATION:
  User enters email + password
    -> supabase.auth.signInWithPassword()
    -> JWT session created
    -> profile fetched (roles, school_id, schools)
    -> hard redirect to role's home route
    -> ProtectedRoute validates role
    -> FeatureAccessContext loads plan features
    -> Dashboard renders with filtered navigation

SCHOOL ONBOARDING:
  Superadmin fills school + admin details
    -> onboardingService.onboardSchool()
    -> school inserted
    -> admin profile linked/created
    -> admin auth account created (edge function)
    -> triggers auto-seed: tax rules, grading config
    -> audit log recorded
    -> superadmin signed out

SUBSCRIPTION MANAGEMENT:
  Superadmin changes school plan
    -> PlanChangeModal
    -> changeSchoolPlan() updates schools.plan + subscription_start
    -> Audit logged with price diff
    -> Feature access reloaded on next refresh

AVATAR UPLOAD:
  User clicks sidebar avatar
    -> file picker opens (PNG/JPG/WEBP, max 2MB)
    -> uploads to school-assets/avatars/{userId}.{ext}
    -> profiles.photo_url updated
    -> authStore profile refreshed
