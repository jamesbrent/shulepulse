1. EXECUTIVE SUMMARY
================================================================================

ShulePulse is a multi-tenant school management system built on React + Supabase.
The system manages students, teachers, finances, payroll, library, reception,
and administrative functions across multiple schools.

OVERALL SECURITY RATING: 4.8/10

CRITICAL ISSUES:  5
HIGH-RISK ISSUES: 9
MEDIUM ISSUES:    10
LOW-RISK ISSUES:  6
INFORMATIONAL:    5

The most dangerous findings center on:
  (a) Core tables (students, attendance, fee_payments) whose RLS policies exist
      only in the hosted Supabase database, NOT in version-controlled migrations
      — making them unauditable and potentially missing entirely.
  (b) Default passwords for ALL student and parent accounts.
  (c) Stored XSS via dangerouslySetInnerHTML in document generation.
  (d) Cross-tenant file access through public storage buckets.
  (e) Platform-wide auth.users exposure via GRANT SELECT to all authenticated.

IMMEDIATE ACTION REQUIRED on the 5 Critical issues before any production deployment.

Affected Module: Student Onboarding / Registration

VULN-03: Stored XSS via dangerouslySetInnerHTML in Document Generation
────────────────────────────────────────────────────────────────────────────────
ID:         VULN-03
Title:      Stored Cross-Site Scripting in Report Cards & Certificates
Severity:   CRITICAL
Affected Module: Report Cards, Transcripts, Certificates
Affected Component: src/components/students/ReportCard.jsx:593-632 (7 sinks)
                   src/pages/Registrar/Alumni.jsx:891
                   src/pages/Registrar/DocumentsCertificates.jsx:553
Description: HTML strings are built by interpolating user-controlled values
             (student names, school names, subject names, discipline records,
             school logo URLs) into raw HTML without any escaping. These are
             rendered via dangerouslySetInnerHTML. A student named
             '<img src=x onerror=alert(document.cookie)>' or a malicious
             school logo_url containing a script would execute JavaScript
             for any admin/registrar viewing the document.
Security Impact: Full JavaScript execution in admin sessions. Attacker can
                 steal session tokens (stored in localStorage), perform
                 actions as admin, exfiltrate data, or pivot to other schools.

                   2. Navigate to Report Cards, generate report for that student
                   3. The script executes when the report renders
Root Cause: HTML string concatenation instead of JSX rendering. No
            input sanitization/escaping applied to interpolated values.
Recommended Fix: Add an esc() function that HTML-encodes <, >, &, ", '.
                 Apply to ALL interpolated values in HTML string builders.
                 Alternatively, refactor to use JSX templating instead of
                 dangerouslySetInnerHTML.

            query issue without considering the security implications.

VULN-05: Core Table RLS Policies Missing from Version Control
────────────────────────────────────────────────────────────────────────────────
ID:         VULN-05
Title:      Unauditable RLS on Critical Tables (students, attendance, fee_payments)
Severity:   CRITICAL
Affected Module: Database / All features
Affected Component: supabase/migrations/ (absence of policies)
Description: The following critical tables have NO RLS policy definitions in
             any migration file in the repository:
               - students (core PII table — 0 policies in repo)
               - attendance (0 policies in repo)
               - fee_payments (0 ENABLE ROW LEVEL SECURITY in repo)
               - classes, subjects (0 policies in repo)
             These tables are managed directly in the hosted Supabase dashboard,
             making them unauditable from code. If RLS is not enabled on these
             tables, any authenticated user can read/write all schools' data.
Security Impact: If RLS is disabled or misconfigured on these tables:
                 - Any user can read all students across all schools
                 - Any user can modify any student record
                 - Any user can read all financial payment data
                 This is the single most dangerous class of vulnerability.
Safe Reproduction: Run against live DB:
                   SELECT relname, relrowsecurity FROM pg_class
                   WHERE relnamespace='public'::regnamespace AND relkind='r'
                   AND relname IN ('students','attendance','fee_payments');
Root Cause: Tables created/managed outside the migration system. RLS policies
            applied via dashboard UI instead of version-controlled SQL.
Recommended Fix: Create migration files that ENABLE ROW LEVEL SECURITY and
                 DEFINE POLICIES for all critical tables. Use the Supabase
                 CLI to pull existing policies from the live DB and commit
                 them to version control.
Priority: PHASE 1 — IMMEDIATE

7. DATA BREACH RISK ASSESSMENT
================================================================================

SCENARIO 1: School A accessing School B data
  LIKELIHOOD: MEDIUM-HIGH
  VECTORS:
    - If students/attendance/fee_payments tables lack RLS (VULN-05),
      any user can query cross-school data
    - Storage buckets allow cross-tenant file access (VULN-07)
    - School switcher writes school_id from client (VULN-09)
  IMPACT: Complete cross-tenant data breach

SCENARIO 2: Student accessing another student's records
  LIKELIHOOD: LOW-MEDIUM (depends on RLS)
  VECTORS:
    - Student portal resolves by email, not by route param (mitigated)
    - But if students table lacks RLS, student can query any record
    - StudentDocuments path is not school-scoped
  IMPACT: Student privacy breach (grades, fees, personal info)

SCENARIO 3: Parent accessing another student
  LIKELIHOOD: LOW-MEDIUM
  VECTORS:
    - Parent portal filters by parent_id (good)
    - But attendance/fee tables may lack RLS (VULN-29)
  IMPACT: Parent sees other students' attendance and fee data

SCENARIO 4: Teacher accessing payroll
  LIKELIHOOD: HIGH (confirmed)
  VECTORS:
    - staff_select_* policies allow teacher role to SELECT payroll tables
    - Direct API query returns salary data for all staff in school
  IMPACT: Full salary exposure for all staff

SCENARIO 5: Exposed public documents
  LIKELIHOOD: HIGH (confirmed)
  VECTORS:
    - finance-attachments bucket is public with no auth check
    - school-assets bucket is public
    - student documents use public URLs
  IMPACT: Financial documents, student records publicly accessible

SCENARIO 6: Privilege escalation via stored XSS
  LIKELIHOOD: MEDIUM
  VECTORS:
    - Student name XSS → admin views report card → session stolen
    - Stolen session = full admin access across all schools
  IMPACT: Complete system compromise

SCENARIO 7: Default password account takeover
  LIKELIHOOD: HIGH (trivial)
  VECTORS:
    - Student@123 works for ALL student accounts
    - Parent@123 works for ALL parent accounts
    - Bulk password reset available in admin UI
  IMPACT: Mass account takeover
