================================================================================
REMAINING HIGH RISKS
================================================================================

1. Cross-school data access on "FOR ALL" policies
   - Many tables have FOR ALL policies (not role-restricted)
   - Students/parents in same school can technically CRUD other school data
   - Example: students can update timetable_entries, library, discipline records
   - Mitigation: Requires per-table role-based policy rewrite (Phase 2)

2. profiles table SELECT allows same-school PII access
   - Any authenticated user in a school can read all staff/parent/student PII
   - Should be restricted to admin/deputy_admin for non-self profiles

3. teachers table allows student/parent CRUD
   - Same-school users can update/delete teacher records
   - Should be restricted to admin roles for writes

4. platform_settings contains plaintext API keys in defaults
   - email_password, mpesa_consumer_secret, stripe_secret_key etc.
   - Should be encrypted at rest or moved to Supabase Vault

5. Fee payment ledger insertion not atomic with payment
   - If GL posting fails, payment + ledger persist but user sees error
   - Should use a database transaction/RPC

6. Duplicate AP payment request check is client-only
   - Two concurrent submissions can both pass the in-memory check
   - Should add a unique DB constraint on (run_id, status != 'cancelled')

RECOMMENDED NEXT SECURITY PHASE
================================================================================

Phase 2 should address:

1. Role-based write restrictions on FOR ALL policies
   - Students/parents should not be able to write teacher records, timetables,
     library, discipline, reception, departments, non_teaching_staff
   - Requires per-table policy rewrite with INSERT/UPDATE/DELETE role gates

2. profiles table PII access restriction
   - Admin-only SELECT for non-self profiles
   - Parents/students can only read their own profile

3. Atomic financial transactions
   - Fee payment + ledger + GL posting should be in a single RPC
   - Prevents partial writes leaving inconsistent records

4. DB-level constraints for duplicate prevention
   - Unique constraint on (run_id) for payroll_payment_requests where status != 'cancelled'
   - CHECK constraint on fee_payments for duplicate amount+student+term+date

5. Platform settings encryption
   - Move API keys from plaintext to Supabase Vault or encrypted column

6. Storage file-type validation
   - StudentDocuments.jsx uploads without MIME-type validation
   - Should enforce allowed types and file size limits server-side

7. User impersonation controls
   - RoleSwitcher allows any admin to assume any role
   - Should log impersonation and require justification
